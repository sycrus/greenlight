# Product Requirements Document
## Agentic AI Platform with Generative UI

**Version:** 0.2
**Status:** Active — Phase 1 in development
**Created from:** Architecture discovery session + pre-build alignment (2026-04-14)

---

## 1. Problem Statement

Build a production-grade agentic AI platform that delivers brand-consistent, customer-facing interactions through a generative UI layer. The system must maintain conversational coherence across sessions, enforce brand standards deterministically, support complex multi-step workflows, and be deployable on GCP or Azure with enterprise-grade observability and memory management.

The platform replaces fragile system-prompt-based approaches with a structured, layered architecture where behavioural rules, retrieval, orchestration, memory, and UI rendering are each handled by purpose-built components with clean interfaces between them.

---

## 2. Goals

- Deploy a customer-facing AI agent that reliably enforces brand tone, guidelines, and compliance rules on every interaction
- Support multi-session continuity through structured memory — users should not need to re-explain context across conversations
- Render dynamic, brand-consistent UI components generated by the agent at runtime
- Provide full observability into agent reasoning, tool calls, memory operations, and UI decisions
- Maintain architectural flexibility — any layer should be replaceable without rewriting adjacent layers

---

## 3. Non-Goals (for this version)

- Fine-tuning or training custom LLMs
- Open-ended generative UI (agent generates arbitrary markup) — pattern is constrained to registered components only
- Multi-tenant isolation (single-tenant deployment initially)
- Voice or audio modalities

**Deferred to Phase 2** (architecture is designed to accommodate these without rework):

- LlamaIndex / RAG retrieval — tool call sites are stubbed in the agent code
- MCP servers — Contentful brand context accessed via placeholder YAML in Phase 1
- Contentful live integration — guidelines are in static YAML, sync job not built yet
- GDPR erasure workflow, forgetting policies, retention TTLs — compliance deferred pending legal input
- Langfuse / LangSmith integration — OTel traces to console in Phase 1
- Storybook component library — Shadcn used in Phase 1, Storybook added in Phase 2
- CopilotKit React hooks — raw AG-UI SSE client used in Phase 1; CopilotKit is a drop-in swap
- Intent Agent behavioral signals — context injection at proxy layer, frontend signal collector, signal-aware Parlant guidelines (see Section 4.11)

## 4. Stack Decisions

All decisions below are confirmed and should be treated as architectural constraints in implementation.

### 4.0 Languages and Frameworks

**Backend:** TypeScript (`@langchain/langgraph`, `@anthropic-ai/sdk`, Express). Python is used only for the Parlant service, which runs as a separate Docker container called over HTTP.

**Frontend:** Next.js (App Router) + React + Tailwind CSS.

**Monorepo:** pnpm workspaces. Structure:

```
gen-ux/
├── apps/
│   ├── agent/        ← TypeScript Express + LangGraph
│   └── frontend/     ← Next.js
├── packages/
│   └── design-system/ ← component library + registry.json
├── services/
│   └── parlant/      ← Python Docker service
└── skills/           ← SKILL.md behavioral specs
```

**Testing:**
- Backend: Vitest (unit + integration) + Supertest (HTTP endpoints)
- Frontend E2E: Playwright
- Integration tests hit real dependencies — no infrastructure mocks

### 4.1 Orchestration
**LangGraph** (`@langchain/langgraph` — TypeScript SDK)

LangGraph is the orchestration layer — stateful directed graph, checkpoints, human-in-the-loop, conditional routing. `langchain-core` is present as a transitive dependency for message types only (`HumanMessage`, `AIMessage`, `BaseMessage`). No LangChain chains, agents, or integration packages are used directly.

**Graph topology (Phase 1):**

```
START → orchestrator → (conditional) → weather_agent   → END
                                    → customer_service → END
```

Checkpointing uses `MemorySaver` (in-process) in Phase 1. Phase 2 replaces with `PostgresSaver` on Cloud SQL for cross-session continuity. `thread_id = sessionId`.

### 4.2 Behavioural Control
**Parlant** (Apache 2.0, self-hosted on Cloud Run)

**Parlant is the primary orchestrator, concierge persona, and guardrails layer.** LangGraph agents are subagents called as tools when tasks require real data or multi-step workflows.

Parlant has its own LLM call on every turn. It evaluates guidelines against the current conversation context and either:
1. **Responds directly** — for simple exchanges, compliance scenarios, or brand voice responses
2. **Calls a memory tool** — `save_memory` or `recall_memories` (Mem0) for personalisation
3. **Calls LangGraph as an HTTP tool** — when the user needs something actionable (weather, account help, etc.)

```
User message
  ↓
Parlant  (has its own LLM call)
  ├── evaluates brand/tone/compliance guidelines
  ├── simple exchange → responds directly in concierge voice
  ├── user shares preference → save_memory → Mem0
  ├── user asks about themselves → recall_memories → Mem0
  └── actionable request → langgraph_agent tool → POST /chat to LangGraph
        ↓
      LangGraph
        orchestrator → weather_agent | customer_service_agent
        ↓
      response back to Parlant
  ↓
Parlant wraps result in brand tone → User
```

The "concierge personality" is Parlant's guidelines — not a LangGraph agent. LangGraph handles execution; Parlant handles voice, compliance, and memory.

**Deployment:** Self-hosted Python Docker container on Cloud Run. Scale-to-zero in dev (essentially free). Set `min-instances: 1` in production to avoid cold starts (~$30–50/month for a small instance).

**Integration:** Parlant calls the LangGraph agent server via HTTP (`POST /chat`). Decoupled services — either can be swapped without touching the other.

**Phase 1:** Parlant is live as the primary orchestrator with static YAML guidelines (`backend/parlant/config/guidelines.yaml`). Three tools registered: `langgraph_agent`, `save_memory`, `recall_memories`. Memory is backed by Mem0 OSS on port 8080.

**Phase 2:** Guidelines synced from Contentful via webhook.

No account required — pip install or Docker.

### 4.3 LLM Provider
**Anthropic Claude** (via direct `@anthropic-ai/sdk` — not `langchain-anthropic`)

A thin TypeScript provider adapter (`apps/agent/src/providers/anthropic.adapter.ts`) wraps the Anthropic SDK to conform to LangGraph's `langchain-core` message types. Swapping to a different LLM requires only replacing this adapter.

**Model configuration:**

| Context | Model | Rationale |
|---|---|---|
| Default (all agents) | `claude-haiku-4-5-20251001` | Cost-efficient for high-volume interactions |
| Orchestrator override | configurable via `model` param | Can use a smarter model for routing if needed |
| Distillation LLM-as-judge (phase 2) | configurable | May use a different model for memory scoring |

Model is set via `DEFAULT_MODEL` env var and overrideable per-call. No code change required to switch models.

Requires: Anthropic API account and key (console.anthropic.com).

### 4.4 Retrieval (RAG)
**LlamaIndex** (open source) — **Phase 2**

Deferred. The `retrieve_documents(query)` tool call site is stubbed in the agent code with `TODO (phase 2)` comments. The retrieval interface is defined so the tool can be added without changing agent logic.

When built:
- Handles document ingestion, chunking, indexing, embedding, retrieval, and re-ranking
- Exposed to LangGraph as tool calls (`retrieve_documents(query)`) — agent never calls LlamaIndex directly
- Embedding models (BAAI/bge-large-en-v1.5, Cohere multimodal, Gemini Embedding 2) and rerankers (FlagEmbeddingReranker, CohereRerank) are swappable without changing retrieval interface
- Multimodal support via `MultiModalVectorStoreIndex` if brand assets need semantic retrieval

See `skills/rag-query-construction.md` for query construction rules.

### 4.5 Brand and Knowledge Context
**MCP Servers** — **Phase 2** | **Contentful** (headless CMS) — **Phase 2 integration, Phase 1 placeholder**

**Phase 1:** Brand guidelines and Parlant behavioural rules are maintained in `services/parlant/config/guidelines.yaml`. This is the placeholder — edited by hand until Contentful is set up.

**Phase 2:** Contentful becomes the source of truth. The brand team manages content in Contentful without code deployments. A sync job loads Contentful rules into Parlant at startup and re-syncs on webhook events.

MCP servers are deferred entirely to Phase 2. No MCP infrastructure is built until the gateway and auth prerequisites in Section 8 are live.

**Contentful content model:**

| Content Type | Key Fields | Purpose |
|---|---|---|
| `BrandRule` | `id`, `category`, `rule`, `rationale`, `severity`, `tags` | Tone, voice, and style rules evaluated by Parlant per turn |
| `TerminologyEntry` | `approved`, `banned`, `notes` | Approved and banned terms enforced across all responses |
| `ComponentGuideline` | `componentName`, `useWhen`, `neverUseWhen`, `neverCombineWith` | Rules for generative UI component selection |
| `CustomerJourney` | `trigger`, `steps`, `escalationConditions` | Structured workflows for complaint handling, escalation, etc. |
| `ComplianceRule` | `id`, `rule`, `jurisdiction`, `severity` | Legal and compliance constraints, editable by legal team |

Role-based access: brand team edits tone/voice/terminology, legal team edits compliance rules, product team edits component guidelines.

**Contentful → Parlant (behavioural control):**

Parlant maintains its own internal guideline store — it does not query Contentful mid-conversation. A sync job loads Contentful rules into Parlant at startup and re-syncs on Contentful webhook events (publish/unpublish). `BrandRule`, `TerminologyEntry`, and `ComplianceRule` entries are mapped to Parlant guidelines and evaluated turn-by-turn from Parlant's internal store.

```
Contentful publishes rule change
  ↓ webhook
Parlant sync job fetches updated rules via Contentful Delivery API
  → writes to Parlant guideline store
  ↓ next conversation turn
Parlant evaluates updated rules against current context
```

**Contentful → LangGraph (agent guardrails):**

LangGraph accesses Contentful rules via the MCP server as tool calls — used for guardrail checks, component selection guidance (`ComponentGuideline`), and customer journey routing (`CustomerJourney`). The agent queries the MCP server when it needs to validate a decision against brand or compliance rules mid-workflow.

```
LangGraph node needs brand/compliance context
  ↓ tool call
MCP server fetches from Contentful Delivery API
  → returns relevant rules to agent
  ↓
Agent applies rules to current decision
```

Requires: Contentful account (free tier sufficient for development; paid for production content volume).

### 4.6 Generative UI
**AG-UI** (CopilotKit protocol) + **A2UI-shaped JSON schema**

AG-UI is the streaming event transport between LangGraph and the frontend. The agent server emits events over SSE:

| Event | Trigger | Frontend action |
|---|---|---|
| `RUN_STARTED` | Graph invocation begins | Set loading state |
| `TOOL_CALL_START` | Agent calls a tool | Render skeleton component |
| `TOOL_CALL_END` | Tool returns with component spec | Swap skeleton → real component |
| `TEXT_MESSAGE_START/CONTENT/END` | Prose response streaming | Accumulate into message bubble |
| `RUN_FINISHED` | Graph complete | Clear loading state |
| `RUN_ERROR` | Graph error | Show error state |

**Phase 1:** Raw SSE client (`apps/frontend/src/lib/ag-ui/client.ts`) — thin fetch wrapper that parses the event stream and dispatches to handlers. No CopilotKit dependency required.

**Phase 2:** Drop in CopilotKit hooks (`useCopilotChat` from `@copilotkit/react-core`) as a direct replacement for the raw client. Same event protocol — zero backend changes.

**Request path:**

```
Frontend → POST /api/chat (Next.js route) → Parlant (sessions + events) → langgraph_agent tool → POST /chat (agent server SSE)
```

The Next.js API route is the integration point where Parlant will be inserted in Phase 2 (swap `AGENT_URL` for `PARLANT_URL` in the proxy).

No React Server Components / `streamUI` — incompatible with component registry model.

### 4.7 Component System
**Phase 1:** Shadcn (swap target) + **DTCG design tokens placeholder** + **`registry.json`** (manually maintained)
**Phase 2:** Storybook (atoms / molecules) + Style Dictionary + CI-generated `registry.json`

**Phase 1 setup:**

Components live in `packages/design-system`. Shadcn primitives (`Button`, `Input`) are used directly. All imports go through `@gen-ux/design-system` — replacing Shadcn with a design system requires only updating that package, not any consumer code.

`registry.json` is manually maintained in Phase 1. Phase 2 generates it automatically from Storybook story metadata.

**Phase 2 Storybook pattern:**

All components live in Storybook. Each component story (CSF format) includes a custom `registry` metadata block alongside standard args and controls:

```ts
// ProductGrid.stories.ts
export default {
  title: 'Molecules/ProductGrid',
  component: ProductGrid,
  parameters: {
    registry: {
      variants: ['default', 'compact', 'featured'],
      requiredProps: ['items'],
      neverCombineWith: ['HeroBanner', 'PromoBanner'],
      useWhen: 'Displaying a list of product recommendations',
      neverUseWhen: 'Fewer than 2 items — use ProductCard instead',
      skeletonComponent: 'ProductGridSkeleton',
    }
  }
}
```

**Registry generation (CI build step):**

```
Storybook stories (CSF + registry metadata)
  ↓ build-registry script (runs in CI on every Storybook change)
  → registry.json
  ↓
Component registry service (loads registry.json at startup)
  ↓ validates A2UI specs at runtime before render
```

`registry.json` shape:
```json
{
  "ProductGrid": {
    "variants": ["default", "compact", "featured"],
    "requiredProps": ["items"],
    "neverCombineWith": ["HeroBanner", "PromoBanner"],
    "useWhen": "Displaying a list of product recommendations",
    "skeletonComponent": "ProductGridSkeleton"
  }
}
```

The registry service exposes a `validate(spec)` method — returns valid/invalid + reason. Invalid specs are rejected before reaching the renderer; the agent receives a structured error and can self-correct.

**Ownership:** design system / frontend team. Adding or modifying a component requires updating the story metadata — CI regenerates `registry.json` automatically.

**NPM package** — the distributable output of the design system, published as `@yourorg/design-system`:

```
@yourorg/design-system
  ├── components/          # Compiled React components
  │     ├── ProductGrid/
  │     ├── HeroBanner/
  │     └── ...
  ├── tokens/              # Style Dictionary output
  │     ├── tokens.css     # CSS custom properties (consumed by components)
  │     ├── tokens.js      # JS constants
  │     └── tokens.d.ts    # TypeScript types
  ├── registry.json        # Generated registry (consumed by registry service)
  └── index.ts             # Barrel export
```

| Consumer | What it imports |
|---|---|
| Frontend app | `components/` + `tokens/` |
| Component registry service | `registry.json` only |
| Storybook (dev) | Everything — it is the source |

**Design tokens** in DTCG 3-layer format: primitives → semantics → components. Token updates in Figma trigger CI pipeline → Style Dictionary transform → Storybook rebuild → NPM publish.

### 4.8 Memory Architecture
**Mem0** (confirmed) behind a unified `MemoryStore` interface with swappable adapters.

**Adapter pattern:** All agent code interacts only with the `MemoryStore` interface (`apps/agent/src/memory/types.ts`). The `Mem0Adapter` is the current implementation. Writing a `BespokeAdapter` later requires only satisfying the same interface — no other changes.

```typescript
// Swapping adapters is one line in server.ts:
const memoryStore = new BespokeAdapter()  // was: new Mem0Adapter()
```

**Phase 1:** Memory write/read sites are stubbed with `TODO (phase 2)` comments in agent code. `PlaceholderMemoryStore` (in-memory, no persistence) is used automatically when `MEM0_API_KEY` is not set. `Mem0Adapter` activates when the key is provided.

**Phase 2:** Mem0 configured to use pgvector (Cloud SQL) as its vector backend so all data stays in our infrastructure. Full four-type memory architecture below.

Four memory types, all behind a unified `MemoryStore` interface with swappable adapters.

| Type | Store | Purpose | Written by | Read by |
|---|---|---|---|---|
| Working | Redis | Active conversation state, current session | LangGraph (each turn) | LangGraph (each turn) |
| Episodic | pgvector / Weaviate | Past interactions, retrievable by semantic similarity | Distillation job (session end) | LangGraph (session start) |
| Semantic | Postgres + pgvector | User facts, preferences, account data | LangGraph (mid-conversation, hot path) + distillation job | LangGraph (session start) |
| Procedural | Postgres JSONB | Workflow rules, escalation logic, brand execution patterns | Distillation job (learned patterns) | LangGraph (routing decisions), Parlant (journey execution) |
| Checkpoints | Postgres (LangGraph) | Full graph state snapshots, scoped by thread_id | LangGraph (automatic, each node) | LangGraph (resume, human-in-the-loop, recovery) |

**Distillation** is a background job that runs at session end. An LLM-as-judge reviews the full conversation transcript, scores candidate memories for importance, and writes only high-signal findings to the appropriate store. Low-importance content is discarded.

| Found in conversation | Written to |
|---|---|
| Stated user preference ("I prefer email over phone") | Semantic |
| Completed interaction (complaint resolved via escalation) | Episodic |
| Learned pattern (users in this segment reject upsells mid-complaint) | Procedural |

**Distillation triggers:**
- End of session (primary)
- Explicit event signals (purchase complete, complaint resolved, stated user preference)
- Hot path: agent flags high-importance information mid-conversation via memory tool call

**Forgetting policies:**
- TTL per memory type (working: session; episodic: 6–12 months; semantic: until changed; procedural: until explicitly updated)
- Contradiction detection: new memory supersedes conflicting existing memory
- User-driven deletion: supported (GDPR right to erasure)
- Compliance archive: raw checkpoint data archived to GCS (immutable bucket, object versioning) before operational deletion — never discarded without archiving

**Consent record:**
User consent to data retention is stored in Postgres alongside semantic memory, scoped by `user.id`. Consent is checked before any memory write. No memory is written without a valid consent record.

**GDPR erasure workflow:**
A dedicated erasure job (standalone Cloud Run job, triggered by user deletion request) cascades deletion in sequence:

```
Erasure request received (user.id)
  ↓
1. Archive active checkpoints → GCS immutable bucket
  ↓
2. Delete working memory → Redis (flush by user.id key prefix)
  ↓
3. Delete episodic memory → pgvector (delete by user.id filter)
  ↓
4. Delete semantic memory → Postgres + pgvector (delete by user.id)
  ↓
5. Delete procedural memory → Postgres JSONB (delete by user.id)
  ↓
6. Revoke consent record → Postgres (mark as erased, retain tombstone for audit)
  ↓
7. Write erasure completion event → immutable audit log (GCS)
```

Erasure is a first-class workflow, not a database script. Each step is logged to the audit trail. GCS archive data is retained per compliance retention period before final deletion.

**Compaction:** Hierarchical strategy — keep recent N turns verbatim, summarise older turns, discard oldest. Trigger at 70% of model context window.

**Mem0** considered as abstraction layer over memory stores — decision deferred pending complexity assessment.

### 4.9 Observability
**Phase 1:** OpenTelemetry → console (structured JSON). No external tracing backend yet.
**Phase 2:** OpenTelemetry → Langfuse (self-hosted) + LangSmith (dev) + Cloud Monitoring (infrastructure).

**Phase 1 setup:** `ConsoleSpanExporter` in `apps/agent/src/observability/otel.ts`. Swap to `OTLPTraceExporter` for Phase 2 — one line change, no instrumentation rework needed. All spans already carry standard attributes: `user.id`, `session.thread_id`, `agent.node`.

**Full Phase 2 stack:** **OpenTelemetry** (instrumentation standard) + **LangSmith** (LangGraph tracing, dev only) + **Langfuse** (full-stack, self-hosted) + **Cloud Monitoring** (infrastructure)

All spans carry standard attributes: `user.id`, `session.thread_id`, `agent.node`, `mcp.tool`, `memory.type`.

| Tool | Purpose | Environment |
|---|---|---|
| Langfuse (self-hosted on Cloud Run) | Token usage, cost per session/user/node, LLM-as-judge evals, retrieval quality, memory operations | Production + dev |
| LangSmith (free tier) | LangGraph graph execution visualisation, node-level debugging | Dev only — synthetic/sanitised data only, never production customer data |
| Cloud Monitoring | Infrastructure health — Cloud Run, Cloud SQL, Memorystore, request latency, error rates | Production |
| Cloud Logging | Structured operational logs from all services | Production |
| BigQuery (optional) | Long-term cost analytics, cross-service reporting — pipe Langfuse data in | If needed |

**PII scrubbing at the OTel collector:**
All spans pass through an OTel collector transform pipeline before export to Langfuse. The pipeline redacts or hashes PII fields (conversation content, user identifiers beyond `user.id` hash, account details) before traces are written. Raw conversation content is never stored in Langfuse.

**Immutable audit log (GCS):**
A separate audit log — distinct from operational Cloud Logging — is written to a GCS bucket with object versioning and retention lock. Every event in the table below is written here:

| Event | Audit fields |
|---|---|
| Memory read/write | `user.id`, `memory.type`, `agent.node`, timestamp |
| MCP tool call | `service`, `tool`, `user.id`, `session.thread_id`, timestamp |
| Contentful rule change | `rule.id`, `changed_by`, `previous_value`, timestamp |
| Auth event (login, token refresh, permission denied) | `user.id`, `event_type`, `ip`, timestamp |
| GDPR erasure request + each cascade step | `user.id`, `step`, `status`, timestamp |

**Dashboards:**

| Need | Tool |
|---|---|
| Token usage + cost per session/user/node | Langfuse (built-in, configure Anthropic pricing once) |
| LLM quality evals (brand compliance, retrieval quality) | Langfuse |
| Agent graph traces + node debugging | LangSmith (dev only) |
| Infrastructure health (Cloud Run, Cloud SQL, Memorystore) | Cloud Monitoring |
| Alerting (cost spike, error rate, latency breach) | Cloud Monitoring alerts |
| Long-term cost analytics | BigQuery (optional) |

Requires: LangSmith account (free tier: 5k traces/month — smith.langchain.com).

### 4.11 Intent Agent

**Definition:** Reads what progress a user is trying to make from explicit inputs (chat), behavioral signals, or session/world context and routes the experience accordingly.

**Phase 1 (current):** Parlant's guideline evaluation acts as the intent detector using chat input only. The LangGraph orchestrator node performs fine-grained routing (weather vs. customer service) based on message content. No additional mechanism required.

**Phase 2: Context injection at the proxy layer**

The Next.js API route (`frontend/app/src/app/api/chat/route.ts`) enriches each message with a structured context block before forwarding to Parlant. Parlant's existing guideline evaluation then operates on the enriched message — no Parlant architecture changes required.

```
Browser (frontend)
  → collects behavioral signals passively during session
  ↓
POST /api/chat { message, context: { page, dwell_ms, viewed, ... } }
  ↓
Next.js API route  ← context injection happens here
  → appends [context] block to message text before forwarding
  ↓
Input sanitisation middleware
  ↓
Parlant (intent detection + routing)
  → evaluates enriched message against guidelines
  → routes accordingly
```

**Signal taxonomy:**

| Signal | Category | Example values |
|---|---|---|
| `page` | Surface | `/products/credit-cards`, `/complaints/open` |
| `dwell_ms` | Behavioral | `42000` (ms on current page before messaging) |
| `viewed` | Behavioral | `["cashback-card", "travel-card"]` (items seen this session) |
| `referring_page` | Behavioral | `/home` |
| `session_events` | Behavioral | `["added_to_cart", "viewed_pricing"]` |
| `prior_intent` | Session | Resolved intent label from previous turn (stored in LangGraph state) |
| `session_age_ms` | Session | `180000` |
| `world.time_of_day` | World | `morning` / `afternoon` / `evening` |
| `world.campaign` | World | Active campaign tag from CMS or URL param |

**Wire format appended to message by the proxy:**

```
[context]
page: /products/credit-cards
dwell_ms: 42000
viewed: ["cashback-card", "travel-card"]
prior_intent: browse_products
session_age_ms: 180000
[/context]
```

**Parlant guidelines** use signal content to express routing rules in YAML without code changes:

```yaml
# guidelines.yaml example
- condition: "user has been browsing product pages (dwell_ms > 30000) and asks a purchase question"
  action: route to sales specialist via langgraph_agent
  tags: [routing, intent]
```

**Intent recording:** `intent.label` and `intent.signals_used` are added as OTel span attributes on every Parlant evaluation span. Phase 2 Langfuse dashboard surfaces intent distribution and signal-to-routing correlation over time.

## 5. Architecture Overview

### Full architecture (Phase 2 target)

```
User
  ↓
Next.js frontend
  → frontend signal collector captures: page, dwell, viewed items, session events
  ↓ POST /api/chat { message, context: { page, dwell_ms, viewed, ... } }
Next.js API route  ← context injection: appends [context] block to message
  ↓
Input sanitisation middleware
  ↓
Parlant (intent detection + behavioural control — concierge persona + guardrails)
  → own LLM call, evaluates brand/tone/compliance guidelines per turn
  → reads enriched message: chat + behavioral signals + session/world context
  → simple exchanges → responds directly in brand voice
  → actionable requests → POST /chat → LangGraph agent server
      ↓
    LangGraph (orchestration)
      → orchestrator agent → routes to specialist agents
      → stateful graph, checkpoints (Postgres), human-in-the-loop
      → calls tools: retrieve_documents, memory ops, MCP tools
      ↓ (parallel)
    LlamaIndex              MCP Servers             MemoryStore (Mem0)
    (RAG retrieval)         (Contentful brand        (working/episodic/
                             context, policies)       semantic/procedural)
  ↓
AG-UI event stream (SSE) → Next.js frontend
  ↓
Component Registry (validates A2UI spec)
  ↓
Design system components (Shadcn → Storybook)
  ↓
DTCG design tokens
```

### Phase 1 MVP (current)

```
User
  ↓

```

## 8. MCP Gateway Strategy

**Phase 1 (now):** Single MCP server — Contentful brand/compliance context, called by LangGraph only. No gateway. Direct HTTP/SSE, JWT auth via existing IAM, OTel tracing covers tool calls.

**Before adding any further MCP servers**, the following infrastructure must be in place:

| Prerequisite | Detail |
|---|---|
| Gateway | IBM ContextForge (GCP, self-hosted on Cloud Run) deployed and routing MCP traffic |
| Auth | JWT validation centralised at gateway — individual servers trust gateway, not clients directly |
| Role-based access | Per-server permissions defined — which agents/services can call which MCP servers |
| OTel coverage | All MCP tool calls traced with `mcp.tool`, `user.id`, `session.thread_id` before new servers added |
| Input sanitisation | Prompt injection detection middleware live before Parlant — see Section 13 |

Additional MCP servers are expected (CRM, ticketing, web search, etc.) but are out of scope for this version. None should be added until the gateway and auth infrastructure below is live.

---

### 8.1 Authentication Architecture

Three distinct auth contexts, each handled differently:

**End user → Agent**
- OAuth 2.1 + JWT — user authenticates via Authorization Code + PKCE flow and receives a JWT scoped to their identity and entitlements
- PKCE mandatory for all authorization code flows — implicit grant and ROPC are not used
- Exact redirect URI matching enforced — partial matching prohibited
- Refresh tokens for public clients are one-time use (rotation required)
- JWT claims (`user.id`, `user.tier`, `permissions`) propagate through the pipeline via OTel spans
- Claims determine what the agent is permitted to show or do for that user (e.g. premium vs. standard access)

**Service-to-service (internal)**
- JWT with service accounts — each internal service (LangGraph, Parlant, distillation job) has its own identity
- Validated at the gateway for MCP traffic; validated at the service level for memory stores and LlamaIndex
- mTLS (mutual TLS) in production — both sides prove identity, not just the client

**Agent/service → MCP servers (role-based)**

| Pattern | Applied when |
|---|---|
| **RBAC** (Role-Based Access Control) | Service-level permissions — `langgraph-agent` can call `brand-mcp`, not `crm-mcp` |
| **Scoped JWT claims** | Token carries permitted scopes (`mcp:brand:read`, `mcp:crm:write`) — gateway enforces at request time |
| **ABAC** (Attribute-Based Access Control) | Attribute-driven access — EU users restricted to EU-compliant tools, tier-gated capabilities |

Start with RBAC + scoped JWTs enforced at the gateway. Add ABAC when attribute-driven requirements emerge (geo, compliance jurisdiction, user tier).

**Contentful role separation** (brand team vs. legal team vs. product team) is handled by Contentful's native role system — no custom auth required.

---

### 8.2 Gateway Phases

**Phase 2 (when >5 servers or auth complexity grows):**
- IBM ContextForge (Apache 2.0, self-hosted on Cloud Run) as lightweight MCP gateway

**Phase 3 (if third-party SaaS tools needed at scale):** Composio for external integrations (500+ pre-built connectors), keeping internal servers behind own gateway layer.

MCP client configured against a single endpoint URL — switching from direct to gateway requires config change only, not code change.

## 10. Cross-Cutting Principles

These apply to every layer and every implementation decision.

**Abstraction layers everywhere.** No framework or vendor code leaks into business logic. Every external dependency is wrapped behind an interface with a swappable adapter. LLM provider, memory backends, retrieval layer, MCP transport, UI spec format — all replaceable without touching agent logic.

**OTel span taxonomy defined upfront.** Standard attributes on every span before any agent code is written: `user.id`, `session.thread_id`, `agent.node`, `mcp.tool`, `memory.type`. Retrofitting is significantly harder.

**PRD and SKILL.md as the durable asset.** The technology stack is an implementation detail. The requirements, brand rules, and behavioural standards are the thing that doesn't change. Document them in structured, machine-readable form from the start.

**LangGraph, not LangChain.** When describing the stack, the correct statement is "we're building on LangGraph." `langchain-core` is a transitive dependency for message types. No other LangChain packages.

**Component registry before generative UI.** The Storybook component library must be clean, consistently named, and machine-readable before generative UI is layered on top. The AI amplifies the quality of the design system — messy system produces confidently wrong output at scale.

**Test-driven development.** All implementation is test-driven. Tests are written before or alongside implementation — not after.

| Layer | Framework | Scope |
|---|---|---|
| Backend unit + integration | Vitest + Supertest | Tool handlers, adapters, LangGraph nodes, HTTP endpoints |
| Frontend E2E | Playwright | Full conversation flows, component rendering, skeleton swap |

Integration tests hit real dependencies — no mocks for infrastructure boundaries. Unit tests for pure logic (routing decisions, schema validation) run without network calls. Integration tests requiring `ANTHROPIC_API_KEY` are skipped automatically when the key is absent (CI uses the key; local dev can run unit-only). The success criteria in Section 15 are automated test suites, not manual checks.

## 13. Security and Compliance

### 13.1 Data Classification

| Data | Classification | Handling |
|---|---|---|
| Conversation transcripts | PII / Confidential | Scrubbed at OTel collector before tracing — never stored in Langfuse verbatim |
| Semantic memory (user facts, preferences) | PII | GDPR erasure cascades here — consent required before write |
| Episodic memory (past interactions) | PII | Same |
| Working memory (active session) | PII | TTL = session — deleted on session end |
| Checkpoint data | Potentially PII | Archived to GCS before deletion — never discarded without archiving |
| Brand rules (Contentful) | Internal | No PII — no special handling |
| LLM traces (Langfuse) | Potentially PII | PII scrubbed at OTel collector before export |
| Audit log (GCS) | Confidential | Immutable — object versioning + retention lock |

### 13.2 Input Sanitisation and Prompt Injection

A sanitisation middleware layer sits between the user and Parlant — every incoming message passes through it before any agent processing:

```
User message
  ↓
Input sanitisation middleware
  → strip/escape injection patterns (role overrides, instruction injections)
  → validate message length and structure
  → hash/redact PII before it enters the trace pipeline
  ↓
Parlant (behavioural control)
```

The component registry provides a second guard: the agent can only render registered components, preventing hallucinated or injected component specs from reaching the renderer.

### 13.3 Network Security

All internal GCP services communicate over a private VPC:
- Cloud Run services on internal ingress — not publicly addressable
- Cloud SQL and Memorystore on private IPs only
- Only the customer-facing agent endpoint has public ingress
- VPC Service Controls to prevent data exfiltration across service perimeters

### 13.4 Encryption

| Store | Encryption | Key management |
|---|---|---|
| Cloud SQL | At rest (AES-256) | CMEK via Cloud KMS |
| Memorystore | At rest | CMEK via Cloud KMS |
| GCS (audit log, archive) | At rest | CMEK via Cloud KMS + retention lock |
| Secret Manager | At rest | CMEK via Cloud KMS |
| All services | In transit | TLS 1.2+ enforced |
| Service-to-service | In transit | mTLS in production |

### 13.5 Compliance Targets

Compliance frameworks to certify against are an open decision (Section 11) pending legal input. The following controls are built in from day one regardless of which frameworks are chosen:

| Control | Implementation |
|---|---|
| Audit logging | Immutable GCS audit log — all memory, auth, MCP, and erasure events |
| Data minimisation | PII scrubbed at OTel collector — only necessary data stored |
| Right to erasure | GDPR erasure workflow — first-class job, full cascade, audit trail |
| Consent | Consent record in Postgres — checked before every memory write |
| Encryption at rest | CMEK on all stores |
| Access control | RBAC at MCP gateway, OAuth 2.1 + scoped JWTs for end users, service account JWTs for internal services |
| Secret management | All credentials in Secret Manager — no hardcoded secrets |
| Network isolation | VPC — internal services not publicly reachable |
